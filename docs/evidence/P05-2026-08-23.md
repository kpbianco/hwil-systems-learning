## Figure, control, metric, and unit inventory

Figures and views:

- baseline owner map — ten P04 function contracts versus software/hardware domain, dimensionless Boolean owner;
- complementary baseline resource view — declared capacity used in percent for software work and hardware allocation;
- control-owner sweep — software versus hardware utilization percent while only functions 4–5 move;
- supervision-owner sweep — nominal fit, cancellation-guard availability, and full contract as Boolean results
  while only functions 2, 8, and 9 move under a fixed software stall;
- broken evidence comparison — nominal resource fit, complete report, and resource-only report as Boolean decisions.

Interactive controls:

- control owner: software or hardware, baseline software;
- supervision owner: hardware or software, baseline hardware;
- software capacity: integer 0–60 work units per update, baseline 30;
- hardware capacity: integer 0–60 allocation units, baseline 40;
- application software: available or stalled, baseline available;
- injected boundary event: none, cancellation, or deadline/timeout, baseline none;
- assessment evidence: complete or broken resource-only, baseline complete;
- reset baseline button.

Model metrics and retained contracts:

- function owner, capacity- and software-state-gated execution availability, lost-function list,
  fixed-binding validity, event-guard availability,
  containment status, allocation truth, reported feasibility, false feasibility, and safe-hold-request
  availability — logical or categorical;
- software function contribution and demand — work units per update; baseline 22/30 with margin 8;
- hardware function contribution and demand — allocation units; baseline 22/40 with margin 18;
- domain utilization — percent of declared instructional capacity;
- fixed resource envelope — ten functions by two execution domains; maximum declared capacity 1000 units.

Work units and allocation units are transparent instructional counters, not microseconds, WCET, task or link
utilization, scheduling, path latency, clock rate, FPGA fabric measurements, silicon area, power, or jitter.
Cancellation and deadline/timeout are injected at a named function boundary without event timing or routing.

## Independent audit repairs

Two bounded, read-only audits were run with the primary agent retaining integration ownership. They found and
the implementation repaired these material issues before final verification:

- P05 had renamed `Compute error` and rewritten some P04 contract text. The four P04 name/input/output/failure
  arrays are now carried forward verbatim, asserted in `run_checks.m`, and compared directly against the P04
  source by the durable Python test.
- Event availability originally reflected only owner fault state. It now also requires the event guard's owner
  domain to fit its declared capacity; a combined stalled-software, overloaded-hardware cancellation case
  proves that no guard or logical safe-hold request is claimed from the infeasible domain.
- Static tests now bind the critical owner assignments, inclusive capacity comparisons, cancellation/deadline
  indices, availability and decision equations, assessment selection, false-feasibility equation, and output
  wiring. These checks remain static source evidence, not MATLAB execution.
- The interactive utilization display now maps infinite utilization to a labeled clipped plotting value while
  retaining the true demand, capacity, margin, and decision in its summary.

## Changed invariants

- P05 supplies exactly one domain owner for each of P04's ten functions without renaming or removing a contract.
- Functions 1, 7, and 10 remain fixed software boundaries; functions 3 and 6 remain fixed hardware endpoints;
  control owns functions 4–5 and supervision owns functions 2, 8, and 9 as explicit learner levers.
- The fixed cost vectors are software `[2 2 0 6 8 0 4 2 2 2]` work units per update and hardware
  `[0 3 5 7 9 8 0 3 3 0]` allocation units. Baseline demand is 22/30 and 22/40.
- Complete acceptance requires nominal resource fit, valid fixed bindings, application-software-independent
  supervision, and the relevant scenario boundary. Resource-only evidence can therefore be visibly false.
- With adequate declared hardware capacity, a hardware-owned cancellation or deadline guard remains logically
  available under an application-software stall; a software-owned or capacity-starved guard does not.
  Availability means only that a logical safe-hold request can be emitted.
